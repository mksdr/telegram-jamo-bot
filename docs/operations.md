# 운영과 장애 대응

웹훅 등록과 채팅 권한은 [배포와 설정](deployment.md), 파일과 캡션이 채팅에 표시되는 방식은 [사용법](usage.md)을 참고하세요.

## Cloudflare 리소스

| 리소스                      | 용도                                                                        |
| --------------------------- | --------------------------------------------------------------------------- |
| Workers                     | Telegram 웹훅 수신·인증, 검색어 생성, Telegram Bot API 호출                 |
| SQLite 기반 Durable Objects | `TELEGRAM_UPDATES` 바인딩으로 봇·업데이트별 진행 상태 저장과 중복 처리 방지 |
| Durable Object 알람         | 완료·미완료 기록 정리                                                       |
| Workers Secrets             | 봇 토큰과 웹훅 시크릿 보관                                                  |
| Workers Observability       | 실패, 수동 확인 보류, 원본 삭제 실패 로그 확인                              |

처리 상태는 Durable Object의 SQLite 저장소에 기록합니다. 별도 D1, KV, R2, Queues 바인딩은 필요하지 않습니다. [Cloudflare Durable Objects](https://developers.cloudflare.com/durable-objects/)

## 웹훅 응답

| HTTP 상태 | 의미                                                                                                        |
| --------- | ----------------------------------------------------------------------------------------------------------- |
| 200       | 처리할 필요가 없는 업데이트를 건너뛰었거나, 처리 완료 또는 수동 확인 상태를 저장했습니다.                   |
| 400       | JSON 본문 또는 `update_id`가 유효하지 않습니다.                                                             |
| 401       | 웹훅 시크릿 헤더가 없거나 설정값과 일치하지 않습니다.                                                       |
| 500       | 처리 대상 업데이트를 받았으나 봇 토큰이 설정되지 않았습니다.                                                |
| 503       | 웹훅 시크릿이 설정되지 않았거나, 작업 예산이 소진됐거나, 일시적 API·저장 오류로 작업을 완료하지 못했습니다. |

인증과 업데이트 ID 검증을 통과한 요청 중 허용 목록에서 제외된 채팅, 잘못된 허용 목록 설정, 일반 텍스트, 미지원 첨부, 봇 발신 메시지, 검색어를 만들 수 없는 파일은 Durable Object 조회와 Telegram API 호출 없이 건너뜁니다.

## 자동 재시도

같은 봇의 같은 `update_id`로 들어온 동시 요청은 하나의 작업을 공유합니다. 재시도에는 처음 저장한 데이터와 검색어 임계값을 사용하고, 확인된 전송은 건너뜁니다. 이미 게시한 답글을 포함해 업데이트당 최대 두 개의 검색 답글을 게시합니다.

- API 호출과 응답 본문 읽기는 한 번에 최대 5초이며, 한 처리 시도의 API 작업 예산은 20초입니다. 예산을 소진하면 다음 웹훅 재시도에서 이어갑니다. Telegram은 재시도 횟수를 제한하므로 Workers Logs의 `Telegram update incomplete`와 `Telegram update processing failed`를 확인하세요.
- 429 응답에 유효한 `parameters.retry_after`가 있으면 그 값으로 재시도 가능 시각을 저장합니다. 그전까지는 API를 다시 호출하지 않고 503과 `Retry-After`를 반환합니다. Worker가 저장된 시각을 직접 확인합니다. [Telegram 오류 매개변수](https://core.telegram.org/bots/api#responseparameters)
- Telegram API가 해석 가능한 오류 응답으로 408 또는 서버 오류를 반환하면 현재 구현은 최소 1초 뒤 해당 단계를 재시도할 수 있게 합니다. 오류 응답만으로 Telegram에 메시지가 게시되지 않았다고 확인할 수 없으므로 이 경로에는 중복 게시 가능성이 있습니다.
- 게시를 마친 뒤 재시도 가능한 삭제 오류가 발생하면 삭제만 재시도합니다. 삭제에 대한 명확한 400·403 오류는 `Could not delete original Telegram message` 로그에 채팅 ID, 원본 메시지 ID, 오류 코드가 남고 작업은 완료 처리됩니다.

## 수동 확인

| 보류 사유                               | 동작                                                                                                                                                                                   |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `delivery_uncertain`                    | 전송 의도를 `pendingSend`로 먼저 저장합니다. 네트워크 타임아웃, 유효하지 않은 응답, 전송 결과 저장 실패 등으로 전송 성공 여부를 확인할 수 없으면 자동 재전송과 원본 삭제를 보류합니다. |
| `resend_failed` 또는 `follow_up_failed` | 전송이 400·403 등 재시도 대상이 아닌 4xx 오류로 명시적으로 거부되면 실패 단계와 코드를 `blockedSend`에 저장합니다. 408·429는 자동 재시도 규칙을 따릅니다.                              |
| `caption_preservation_unverified`       | 이전 캡션 처리 정책으로 이미 재전송된 미완료 작업에서 원본 캡션이나 엔티티 보존 여부를 확인할 수 없으면 원본을 남기고 보류합니다.                                                      |

보류 상태를 저장하면 웹훅은 200을 반환합니다. 저장에 실패하면 503을 반환하며, 다음 요청에서 저장된 전송 의도를 확인해 보류를 기록할 수 있습니다. `Telegram delivery requires reconciliation` 로그에는 `update_id`와 보류 사유만 있어 그 로그만으로는 원본 채팅이나 메시지를 식별할 수 없습니다. 같은 웹훅을 다시 보내도 보류는 해제되지 않으며, 공개 해제 엔드포인트는 없습니다.

채팅과 원본을 별도로 확인할 수 있다면 Telegram에서 재전송 파일과 답글이 실제 게시됐는지, 봇 권한에 문제가 없는지 확인하세요. 필요한 게시만 수동으로 마무리하고 원본을 삭제하기 전에는 대체 파일과 답글을 확인합니다. 미게시가 확인되고 원인이 해결된 경우 새 업로드로 처리할 수 있습니다. 게시 결과를 확인할 수 없다면 중복 게시를 피하기 위해 원본을 삭제하거나 파일을 다시 올리지 마세요.

## 저장과 데이터 보존

미완료 작업에는 업데이트·채팅·메시지·포럼 주제 ID, 선택된 첨부의 파일 ID와 검색어 생성에 쓰이는 이름, 캡션과 캡션 엔티티, 검색어 임계값, 진행 상태가 저장됩니다. 캡션 엔티티에는 멘션 사용자 정보가 포함될 수 있습니다. 봇 토큰과 웹훅 시크릿은 이 처리 기록에 저장하지 않습니다.

- **완료 기록**은 활성 저장소에 처리 결과만 남기고 완료 후 7일에 정리 알람을 실행합니다.
- **미완료 기록**은 수동 확인 상태를 포함합니다. 처음 기록한 실패를 기준으로 60일 후 만료되며, 실패 기록 전에 중단된 신규 작업은 최초 처리 시점이 기준입니다. 이후 재시도로 기간을 연장하지 않습니다. 알람이나 만료 후 웹훅이 본문과 진행 상태를 `expired_update` 결과로 바꿉니다. 그 결과를 보존하는 7일 동안 중복 요청은 Telegram API 호출 없이 HTTP 200을 받습니다.

### 이전 버전의 기록

- 만료 시각이 없는 이전 미완료 기록에는 발신자와 채팅 정보를 포함한 전체 업데이트가 남아 있을 수 있습니다. 처리 대상 웹훅이 다시 들어오면 데이터가 필요한 필드로 줄어들고 60일 정리 알람이 설정됩니다. 기존 알람이 먼저 실행되면 그 시점부터 60일을 계산하며, 이때 전체 업데이트는 아직 남아 있을 수 있습니다. 새 요청과 기존 알람이 모두 없는 기록은 운영자가 별도로 정리해야 합니다.
- 이전 완료 기록에 전체 업데이트가 남아 있으면 처리 대상 중복 요청에서 결과만 남기고 기존 삭제 시각을 유지합니다. 중복 요청이 없으면 기존 삭제 알람이 실행될 때까지 전체 업데이트가 남을 수 있습니다.

### SQLite 시점 복구

SQLite 기반 Durable Object의 시점 복구(PITR)는 최근 30일 이내의 저장 상태를 복원할 수 있습니다. 활성 저장소에서 본문이나 기록을 삭제한 뒤에도 삭제 전 시점이 복구 범위에 있으면 해당 데이터가 다시 나타날 수 있습니다. 저장소 접근 권한과 로그 공유 범위 및 보존 정책을 관리하세요. [Cloudflare 시점 복구 문서](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#pitr-point-in-time-recovery-api)
